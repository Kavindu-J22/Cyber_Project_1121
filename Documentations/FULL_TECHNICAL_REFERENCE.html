Triplet Loss — Training Mechanics

📐 Triplet Loss Formula

L = max(0, d(Anchor, Positive) − d(Anchor, Negative) + margin)

  • Anchor: Reference face image of the enrolled user
  • Positive: Different image of the same person (same identity)
  • Negative: Image of a different person (different identity)
  • margin: 0.2–0.5 — forces separation between classes
  • d(): L2 Euclidean distance in embedding space

The model learns: "keep same-person embeddings close together, push different-person embeddings far apart."

Training Cycle — Step by Step

1

Data Loading & Preprocessing

Load face images → resize to 224×224 → apply ImageNet normalization. Augment with random flip, brightness ±20%, rotation ±15°.

2

Triplet Mining

For each batch: select (Anchor, Positive, Negative) triplets. Use hard negative mining — find the hardest negatives (closest non-matching face) to accelerate convergence.

3

Forward Pass

Pass Anchor, Positive, Negative through ResNet50 backbone → FC → L2-normalize. Produces three 128-D unit vectors.

4

Loss Computation

Compute Triplet Loss. If loss > 0, model has room to improve. Semi-hard triplets are preferred in early epochs; hard triplets later.

5

Backpropagation & Update

Adam optimizer computes gradients through the entire network. Cosine LR scheduler reduces lr each epoch. Gradient clipping at 1.0 prevents exploding gradients.

6

Validation & Checkpoint

Every 5 epochs: compute EER on held-out pairs. Save checkpoint if EER improves. Early stopping if no improvement for 15 epochs.

7

Threshold Calibration

After training: sweep cosine similarity thresholds from 0.6–0.95. Select threshold that minimises FAR + FRR intersection (EER point). Result: 0.8096.

SE-Res2Net Attention — The Core Innovation

🔬 Squeeze-and-Excitation + Res2Net Block

Each ECAPA-TDNN block uses a hybrid of two attention mechanisms:

  • Res2Net: Hierarchical multi-scale feature extraction within a single block. Features are split into groups that process at different resolutions, then concatenated.
  • SE (Squeeze-and-Excitation): Channel-wise attention. Global average pooling → FC → Sigmoid → element-wise multiplication. Tells the network which frequency channels matter most for this speaker.

Result: ECAPA-TDNN captures both local spectral patterns and long-range temporal context — essential for speaker identity.

Audio Preprocessing Pipeline

1

Browser Recording

getUserMedia({audio}) → MediaRecorder (WebM/Opus) → 5-second clip. AudioContext.decodeAudioData() → PCM float32 → WAV (16-bit, 16kHz, mono) with custom WAV header writer.

2

Voice Activity Detection (VAD)

Energy-based VAD: RMS energy of each 25ms frame computed. Frames below threshold (0.001 energy) discarded. Ensures model only processes actual speech, not silence or background noise.

3

Segmentation

Audio split into 2.5-second windows with 50% overlap (1.25s step). Each window processed independently by ECAPA-TDNN, then embeddings averaged for final result.

4

Log Mel-Filterbank Extraction

25ms Hamming-windowed FFT → 80 triangular Mel filter banks → log compression. This mimics human auditory perception — the critical features for speaker identity.

5

ECAPA-TDNN Inference

5 Conv1D blocks with SE-Res2Net attention → Attentive Statistics Pooling → 192-D embedding. Total: ~14.8M parameters. Inference: ~185ms per 5s clip (CPU).

1.3 Keystroke Dynamics — Deep MLP + Triplet Loss

Port 8002 PyTorch FastAPI Deep MLP 38-D Features → 128-D Embedding

Overview

The Keystroke Dynamics service authenticates the doctor by analysing their unique typing rhythm. It captures three timing features — Hold time (H), Down-Down time (DD), and Up-Down time (UD) — computes statistical aggregates, and feeds a 38-dimensional feature vector into a Deep MLP that outputs a 128-D embedding for cosine similarity comparison.

Feature Engineering — 38-Dimensional Input Vector

⌨️ Raw Timing Features (31 values)

  • Hold Time (H): Duration key is held down = keyUp.timestamp − keyDown.timestamp (seconds)
  • Down-Down (DD): Time between consecutive key presses = nextKeyDown − prevKeyDown
  • Up-Down (UD): Time between key release and next press = nextKeyDown − prevKeyUp

📊 Statistical Features (7 values)

Computed over the 31 timing values: mean, std, median, min, max, Q1 (25th percentile), Q3 (75th percentile). Pad with zeros if fewer than 31 events captured. Total: 31 + 7 = 38-D feature vector.

1.4 Mouse Movement Analysis — Siamese MLP + Hard Triplet Mining

Port 8003 PyTorch FastAPI Siamese MLP 128-D Embedding

Overview

Mouse Movement Analysis captures the doctor's unique cursor dynamics — velocity profiles, acceleration, curvature, and click patterns — and uses a Siamese Neural Network with shared weights to learn whether two sequences belong to the same person. Hard Triplet Mining with a larger margin (2.0) ensures strong class separation, critical because mouse behavior is more variable than keystroke timing.

Feature Extraction from Mouse Events

🖱️ Raw Events Captured (minimum 20 per sample)

Each event: { timestamp, x, y, button, state } — captured at every mousemove and click.

  • Velocity: Euclidean distance / time delta between consecutive points (pixels/sec)
  • Acceleration: Rate of velocity change (pixels/sec²)
  • Curvature: Angular change in direction between three consecutive points (radians)
  • Angle: Direction of movement (atan2 of dy/dx)
  • Click patterns: Frequency, position distribution, button preference (Left/Right/Middle)
  • Statistical aggregates: Mean, std, min, max, percentiles over all computed features

Why Siamese Network vs Standard Classifier?

⚠️ Mouse Behavior Challenge

Mouse behavior is highly context-dependent — the same person moves the mouse very differently when filling a form vs scrolling vs clicking buttons. A standard classifier would memorize contexts, not identity. A Siamese network learns relative similarity — "do these two sequences feel like the same person?" — which generalizes better to unseen mouse contexts during a teleconsultation.

2.2 Trust Score Calculation Algorithm

Formula

📐 Weighted Average Trust Score

// From Client/src/pages/Meeting.jsx const computeTrustScore = (face, voice, keystroke, mouse) => { const w = { face: 0.35, voice: 0.30, keystroke: 0.20, mouse: 0.15 }; let total = 0, wSum = 0; if (face !== null) { total += face * w.face; wSum += w.face; } if (voice !== null) { total += voice * w.voice; wSum += w.voice; } if (keystroke !== null) { total += keystroke * w.keystroke; wSum += w.keystroke; } if (mouse !== null) { total += mouse * w.mouse; wSum += w.mouse; } // Normalize by actual weight sum (handles null modalities) const normalized = wSum > 0 ? (total / wSum) : 1.0; return Math.round(normalized * 100); // Returns 0–100 };

💡 Weight Rationale

  • Face (35%): Most reliable biometric in a video call context. Direct visual identity signal.
  • Voice (30%): Second most reliable. Unique vocal tract characteristics. Harder to spoof than behavior.
  • Keystroke (20%): Strong typing rhythm signal but depends on active chat use.
  • Mouse (15%): Highest variance modality. Complements other signals.

Null Handling Strategy

At session start, only captured modalities contribute to the score. Keystroke defaults to 0.5 (50%) when chat is closed (no typing data). All other modalities start as null until first verification completes. The weight sum normalisation ensures the score is always meaningful even with only 1–2 active modalities.

✅ Why Combined Accuracy Exceeds Individual Modalities

The probability that an impostor simultaneously fools all four independent biometric systems is multiplicative: FAR_combined ≈ FAR_face × FAR_voice × FAR_keystroke × FAR_mouse ≈ 0.02 × 0.02 × 0.004 × 0.05 = 0.00000008 (0.000008%). This is why multi-modal fusion is orders of magnitude more secure than any single biometric.

2.4 Zero Trust Lockout Mechanism

Lockout Algorithm

3.3 Step 3 — Backend → ML Services (HTTP Proxy via mlService.js)

The backend's Backend/services/mlService.js is the dedicated proxy layer. It forwards all biometric data from the Express controllers to the appropriate FastAPI service using Axios.

// Backend/services/mlService.js (simplified) const ML_ENDPOINTS = { face: 'http://localhost:8004', voice: 'http://localhost:8001', keystroke: 'http://localhost:8002', mouse: 'http://localhost:8003', }; async verifyFace(imageBuffer, userId) { const form = new FormData(); form.append('file', imageBuffer, { filename:'frame.jpg', contentType:'image/jpeg' }); form.append('user_id', userId); const response = await axios.post(`${ML_ENDPOINTS.face}/verify`, form, { headers: form.getHeaders(), timeout: 10000, // 10s timeout }); return response.data; // { verified, confidence_score, distance } } async verifyVoice(audioBuffer, userId) { const form = new FormData(); form.append('file', audioBuffer, { filename:'audio.wav', contentType:'audio/wav' }); form.append('user_id', userId); return (await axios.post(`${ML_ENDPOINTS.voice}/verify`, form, { headers:form.getHeaders() })).data; } async verifyKeystroke(features, userId) { return (await axios.post(`${ML_ENDPOINTS.keystroke}/verify`, { features, user_id: userId })).data; } async verifyMouse(events, userId) { return (await axios.post(`${ML_ENDPOINTS.mouse}/verify`, { events, user_id: userId })).data; }

🔒 Why a Proxy Layer?

  • Security: ML services are not publicly accessible. Only the backend can reach them (internal network).
  • Auth enforcement: JWT validation happens before the proxy forwards — ML services don't need to implement auth.
  • Error handling: The proxy catches ML service timeouts/errors and returns safe defaults (confidence=0.5) instead of crashing the session.
  • Rate limiting: Backend can throttle requests to ML services to prevent overload.

⚡ Why Socket.IO Instead of HTTP for Score Updates?

HTTP responses go only to the requesting client (the doctor). But the patient also needs to see the doctor's trust score in real time. Socket.IO's room-based broadcasting allows the server to push updates to all participants in a session room simultaneously, with sub-millisecond overhead over the existing WebSocket connection.

✅ Key Architectural Strengths

  • Parallel verification: All 4 modalities run on independent timers — face every 5s, voice every 20s, keystroke+mouse every 10s. No modality blocks another.
  • Graceful degradation: If any ML service is down, the backend returns confidence=0.5 (neutral). Session continues; trust score is simply computed from remaining modalities.
  • Non-blocking UI: All biometric capture and API calls are async. Video call quality (WebRTC) is never interrupted by verification activity.
  • Real-time dual-view: Both doctor and patient see trust scores update in <100ms of a score change, via Socket.IO push.
  • Zero Trust enforcement: Re-verification happens continuously throughout the entire session — not just at login.
